- (decision) Quality gate is a three-stage pipeline per feature, mandatory for every developer: (1) author a written scenario/test-case document under /docs/test-cases/ (line-by-line: actor, request, expected outcome, traced to a requirements section) -> approved by a developer; (2) translate the approved scenario into an E2E test -> approved by a developer; (3) only then write production code until that E2E test passes. Binds: every feature's workflow, start to finish. Prevents: test code or production code being written against an un-agreed scenario, and pushes misunderstanding-catching to the cheapest stage (prose) before either test code or implementation exists.
- (decision) Architecture paradigm is hexagonal (ports & adapters). Binds: domain logic (access resolution, functional-role permissions, resourcing state machine) has no direct dependency on HTTP, persistence, or external integrations. Rule: timetracker and PeopleForce are outbound ports with adapter implementations; inbound HTTP is one adapter into the domain core. Prevents: domain logic coupling to transport/third-party SDKs, which would block fast + fake-backed E2E tests and violate the 'integration failures degrade gracefully' NFR.
- (decision) 'E2E' for stage 2 of the gate = real HTTP request -> real router -> real access-resolution -> real test database. Outbound ports (timetracker, PeopleForce) are bound via DI token to fixture-backed fakes in test configuration, never live third parties. Binds: test infrastructure and CI. Prevents: the mandatory E2E suite being slow, flaky, or blocked by third-party availability, while still satisfying the NFR to assert what the API actually returns.
- (decision) The gate is enforced per feature-owner, not centralized: whoever owns a feature drives its own scenario doc -> E2E test -> code sequence, with approvals happening asynchronously (a developer reviews and signs off, not a blocking handoff to a single dedicated author). Binds: team workflow / branch process. Prevents: any single role or person becoming a serialization point, which would violate the Section 8.2 mandatory-parallelism rule.

- (decision) Vocabulary invariant: entities expose assignFunctionalRole/revokeFunctionalRole only. NO method anywhere named grant/revoke access-role; access roles are never assigned, only computed. Prevents: Section-2 dimension-collapse leaking into code via naming.
- (decision) Access control = AWS-style policy attachment model, one engine for both role dimensions. Tables: Policies {id uuidv7, operator, targetType 'project'|'department'|'user'|..., targetId uuid (polymorphic, NO db FK), targetRole, type 'AR'|'FR', managedBy 'sync'|'admin' provenance}; Permissions {id uuidv7, title, description} (granular feature list per 2.3); UserPolicies {userId, policyId} attachment join (one policy shareable across many users). Managerial facts (user Y manages project X) ARE policy attachments - Project carries NO pmUserId/dmUserId fields and NO users[] array. FR policies runtime-editable via HR Admin UI per 2.3; AR policies seeded, no UI. Prevents: role logic duplicated per context; schema changes when new assignable capabilities (e.g. trainings) arrive.
- (decision) Operator whitelist: '==' and 'IN' only at start. '!=' BARRED from AR/tier-granting rules: negation is satisfied by missing data, inverting fail-closed (user on no projects matches every != condition). If ever needed, != is FR-scoping/deny-only. Exotic/app-side operators barred from the tier-resolution path entirely - AR evaluation must remain expressible as indexed SQL joins.
- (decision) AccessControl facade is the single authorization entry point for all contexts; direct role-flag checks (isManager||isPP style) forbidden everywhere. Two call shapes: isAllowed(feature) for FR capability checks (no target), and tier/section checks which ALWAYS take target employee scope. Combines access-policies-projector + functional-policies-projector.
- (decision) Tier resolution is BULK and live: one recursive SQL query (WITH RECURSIVE) resolves viewer tier (Self/Manager-line/PP/Colleague) to all requested employees in one round trip, walking reports-to edges AND manages-project/department policy attachments as ONE transitive graph (compound chains like reports-to THEN project-manager-of must resolve). Policies join Relationship via indexed uuid columns (targetId=projectId), no FK needed. Section visibility = tier map joined against seeded tier->section mapping. Profile single-target check = degenerate case of same query. Derived access decisions NEVER stored. Polymorphic secondary lookups (second DB call resolving targetIds against the table targetType names) allowed for feature/audience resolution but BARRED from the tier hot path - and when a resolution spans both calls (policy query + per-targetType lookup) the two MUST run inside one transaction, so the rows resolved are consistent with the policies that referenced them. Prevents: per-row walks breaking the 500-record/2s NFR; stale grants; torn reads between policy and target tables; broken compound chains.
- (decision) Org-fact schema: Relationship {id uuidv7, userId FK, type 'direct'|'project', reportsToUserId FK nullable, projectId FK nullable} with CHECK constraint per type - one table, but edge types never share a polymorphic target column. No roleOnProject field: managerial semantics live in policy attachments. At most one active reportsTo edge per user (tree, not graph). Project membership derived solely from Relationship rows. Orphaned policy rows (dangling targetId) fail closed on AR path (join yields zero members -> zero grants); periodic consistency sweep for hygiene.
- (decision) Fail-closed bootstrap: NO superuser derived from data shape - empty reportsTo grants nothing; orphaned data yields LESS access, never more. Top-of-tree gets Manager access via the normal transitive walk, no engine special case. Seed script creates first user with explicitly assigned HR Admin functional role; all admin power flows through ordinary FR assignment, delegable via UI per 2.3. Prevents: privilege escalation via data glitches; hierarchy position granting functional permissions.

- (decision) Generic attachment endpoints (AD-14 cont.): mirrors AD-7's one-policy-engine and AD-11's one-Relationship-table decisions at the HTTP layer instead of inventing bespoke per-feature endpoints. POST /users/:id/policies {type:'AR'|'FR', targetType, targetId, targetRole} creates a Policies+UserPolicies attachment (PP assignment, project/department manager assignment, functional role grant to a user); DELETE /users/:id/policies/:id revokes.
