- (decision) AD:paradigm — Hexagonal (ports & adapters) within DDD bounded contexts, application/domain/infrastructure layout per bounded context under src/<context>/. [ADOPTED] existing repo convention per services/backend/CLAUDE.md and services/backend/.claude/rules/. Binds: all. Prevents: domain logic entangled with Prisma/NestJS/HTTP, defeating the AD-1 red-E2E-before-code gate's testability requirement.
- (decision) AD:domain-purity — domain/ imports nothing from application/, infrastructure/, NestJS transport, Prisma, or SDKs; only domain/services/ may inject a port token via DI, never application/actions/ directly. [ADOPTED] existing repo convention. Binds: user-management, access-control. Prevents: ports becoming a backdoor around domain logic; a controller or action bypassing the domain service that owns the invariant.
- (decision) AD:cross-context-boundary — user-management and access-control each consume the other only through the target's application/ layer exports, never its domain/ or infrastructure/. [ADOPTED] existing repo convention. Binds: both contexts. Prevents: access-control reading user-management's Prisma models directly (or vice versa), which would silently couple schemas across the bounded-context boundary.
- (decision) AD:dependency-direction — Two distinct dependency edges, not a cycle: (1) user-management -> access-control for authorization (every controller/action calls AccessControl.isAllowed / canAccessSection before reading or writing; AD-9-equivalent facade-only rule). (2) access-control -> user-management for org-graph facts (an OrgGraphReaderPort in access-control's domain, implemented by an infrastructure adapter that calls user-management's exported application-layer query service, in-process, live, never cached). Binds: both contexts. Prevents: a real cycle where authorization needs data that needs authorization; keeps the two capabilities (authorize vs supply-facts) as separate module boundaries so each can be built/tested independently.
- (decision) AD:access-roles-computed — Access roles (Self, Reporting line, Project line, PP+HR-line, Colleague) are computed live per request from current relationship facts; never persisted or cached across requests. Binds: access-control. Prevents: a stale permission cache becoming a data leak (project-requirements.md §6). Rule: canAccessSection/isAllowed re-derive from source tables on every call, no derived-decision table.
- (decision) AD:relationship-edges — reports-to and people-partner are modeled as a single Relationship entity with a type discriminator (type='direct' | 'people_partner'), one row per active edge, at most one active edge per (subjectUserId, type) enforced by a partial unique index. Reassignment is DELETE-then-POST (or an atomic replace expecting the current edge id); a conflicting concurrent write returns 409. [ADOPTED/extended] matches already-approved DEC-UM-005 (reports-to) and CC-04's settled zero-or-one PP cardinality, extended to PP by the same shape for consistency and to give PP the same CAS-safe write contract CC-04 asked for. Binds: user-management (owns table + write contract), access-control (reads live for graph walks).
- (decision) AD:department-membership — department membership is a direct FK (User.departmentId, exactly one, never null) plus Department.parentId self-nesting for the tree and Department.managerId for who manages it — not a Relationship edge, because cardinality is exactly-one (not zero-or-one) and the traversal is a tree walk (recursive over Department.parentId), not a person-to-person graph walk. Binds: user-management (schema), access-control (reads live for department-tree audience). Prevents: forcing department into the Relationship-edge shape used for reports-to/PP, which would blur two structurally different traversals (person graph vs department tree) into one query pattern.
- (decision) AD:relationship-journal — a single RelationshipJournal table (actor, subjectUserId, fieldType enum[manager,people_partner,department,department_manager], beforeValue, afterValue, timestamp) records every write to the four access-switch fields uniformly (project-requirements.md §3.4), independent of whether the underlying storage is a Relationship edge or a Department/User FK. Written in the same transaction as the field change. Binds: user-management. Prevents: two different journal shapes for reports-to vs department changes, which would make 'readable by full-profile-access holders and current manager/PP' (§3.4) a per-field special case instead of one query.
- (decision) AD:no-self-assignment — every write to manager, people-partner, department, or department-manager is validated in the domain service (never the controller) against the actor's own current entitlement before persisting; an actor cannot set themselves as the new value. [Rule, project-requirements.md §2.1 'No self-assignment']. Binds: user-management domain/services/relationship.service.ts-equivalent. Prevents: a self-assignment check living only in a guard/controller where a second write path (e.g. a future bulk-import) could bypass it.
- (decision) AD:functional-roles-as-data — functional roles and their permissions are persisted data (Policy, Permission catalog, PolicyPermission join, UserPolicy assignment), administrable through a /roles API with no deploy and no schema change (project-requirements.md §2.3). Binds: access-control (owns tables + admin API), user-management (never stores a role flag). Prevents: 'is a DM' or any role name hard-coded as a permission check anywhere outside access-control.
- (decision) AD:full-profile-access-separate-grant — full profile access (§2.4) is its own table (FullProfileAccessGrant: userId, grantedBy, grantedAt, revokedAt) independent of Policy/UserPolicy, with a domain-service invariant blocking revocation of the last active holder and blocking self-grant. Binds: access-control. Prevents: bundling full-profile access into a functional role, which the spec explicitly forbids and which would make 'remove the last holder' unenforceable as a role-permission toggle.
- (decision) AD:two-extensibility-models — the base section-access matrix (S1-S16 x audience -> none/read/write, project-requirements.md §3.2) is a versioned code constant inside access-control's domain layer, not a DB table: it is NORMATIVE and not user-editable. Functional-role permissions ARE DB data and admin-editable (AD:functional-roles-as-data). Binds: access-control. Prevents: the two genuinely different extensibility requirements (fixed-and-code-owned vs runtime-and-admin-owned) collapsing into one 'everything is a permission row' table, which would let someone accidentally make S2 access admin-configurable when the spec requires it fixed.
- (decision) AD:project-line-narrower-set — Project line audience (PM/DM of a person's projects, transitively upward through project-management only) resolves to a narrower per-section set than Reporting/PP: no S2, no S3, S5 limited to CV+certificates, per project-requirements.md §3.3.2. Implemented as a second narrowing pass applied after audience resolution, not a separate copy of the base matrix. Binds: access-control. Prevents: a second full S1-S16 matrix table drifting from the first when one gets edited and the other doesn't.
- (decision) AD:pp-hr-line — PP HR-line resolution reuses the same Relationship type='direct' reports-to edges used for Reporting line, starting from the assigned PP and walking upward, filtered to nodes whose Department is HR (project-requirements.md §2.1 'restricted to the HR department'). No separate table. Binds: access-control. Prevents: a duplicate manager-chain representation solely for HR that could diverge from the one true reports-to graph.
- (decision) AD:audience-merge — when an actor simultaneously qualifies for more than one audience toward the same target (e.g. Reporting line and PP), the effective per-section access is the best-of merge: write > read > none, evaluated per section independently. Self is evaluated first and is exclusive of all manager-derived columns. [Sourced: kept SPEC-access-control-facade-audience-resolution.md constraints]. Binds: access-control.
- (decision) AD:departure-scheduling — a Departure record (userId, effectiveDate, reason, recordedBy, recordedAt, appliedAt nullable) is written on record-departure (Story 5.1), separate from EmploymentStatus. Recording is blocked while the subject still manages anyone/any department or is anyone's PP (project-requirements.md §4.16), checked via the same live relationship queries as AD:relationship-edges. Binds: user-management. Prevents: conflating 'scheduled' and 'applied' into one status flip, which cannot represent a future effective date.
- (decision) AD:departure-executor — a NestJS scheduled task polls for due, unapplied Departures (effectiveDate <= now() AND appliedAt IS NULL) using SELECT...FOR UPDATE SKIP LOCKED, and applies the full Story 5.2 side-effect bundle (EmploymentStatus row closed+reopened as dismissed, open action items cancelled, active mentorship pairs auto-closed with system note, User.isActive=false) plus setting appliedAt, all in one transaction per due row. Idempotent by construction: appliedAt gates re-selection, so a retry after partial failure (transaction rolled back, appliedAt still null) simply re-attempts the whole bundle cleanly. No message queue / new infra: reuses the existing PostgreSQL dependency (boring technology). [Resolves CC-06: durable, retry-safe, exactly-once effective-date executor]. Binds: user-management.
- (decision) AD:departure-safe-authorization — AccessControl's live checks treat an actor or target as departed once Departure.effectiveDate <= now(), independent of whether the executor's appliedAt has landed yet — i.e. authorization reads the schedule directly, not just the materialized EmploymentStatus, so a lagging worker never grants a window of stale access. [Resolves CAP-5 'departure-safe authorization' from kept SPEC-access-control-facade-audience-resolution.md]. This overrides the normal 15-minute project-line revocation window: departure access loss is immediate, at the effective date, not next-sync. Binds: access-control.
- (decision) AD:employment-status-model — EmploymentStatus is an append-only time-bounded record per user (status enum[active,dismissed], startDate, endDate nullable) — one open row (endDate null) at a time, closed and superseded rather than updated in place, per the existing immutable-event-table convention in services/backend/.claude/rules/nest-prisma.md. Binds: user-management. [ADOPTED existing repo convention, extended to this new table].
- (decision) AD:career-timeline-sync-write — every system-generated UserEvents row is written synchronously, in the same transaction as the domain mutation that causes it, via an explicit call from that use case's application-layer code — no event bus, no NestJS EventEmitterModule pub/sub, no generic table-change listener. [ADOPTED, restates the binding rule already stated inline in the kept epics.md for Epic 3 — this AD gives it a spine home again since the prior spine's AD-11 was removed]. Binds: user-management. Prevents: an async listener silently dropping an event on transaction rollback, leaving S9 incomplete.
- (decision) AD:career-timeline-corrections — UserEvents is append-only; a correction is expressed as soft-deleting the wrong row (deletedAt) and appending a new correct row, never an in-place field update, per services/backend/.claude/rules/nest-prisma.md's existing convention for event/log tables. Binds: user-management.
- (decision) AD:auth-token-split — two different token kinds, deliberately: (1) magic-link token — opaque random value, hashed at rest, DB-backed (MagicLinkToken: userId, tokenHash, expiresAt, consumedAt), single-use, because replay-prevention (DEC-UM-004) needs server-side state a stateless token can't provide; (2) session/access token — stateless signed JWT (userId, issuedAt, expiry) issued only after successful magic-link consumption, no server-side session table, re-authentication is via requesting a new magic link (no refresh-token flow in scope). Binds: user-management (auth flow), access-control (reads the JWT's userId as the authenticated actor, does not otherwise interpret it).
- (decision) AD:enumeration-safety — POST /auth/magic-link returns an identical 200 response body shape and dispatches zero email for an unknown OR a deactivated/dismissed workEmail, exactly as for a known active one; the endpoint never reveals account existence or status. [ADOPTED, DEC-UM-004 + DEC-UM-012]. Binds: user-management.
- (decision) AD:denial-convention — leak-safe HTTP status convention across both contexts: 401 missing/invalid token; 403 valid token but missing functional permission, or a write attempted against read-only access; 404 for a no-access section or a hidden field (never reveals the section/field exists); absent payload data is a missing key, never a null value. [ADOPTED, already-approved in kept docs/test-cases/access-control/README.md and SPEC-access-control-facade-audience-resolution.md]. Binds: both contexts, every controller.
- (decision) AD:query-cost-budget — every access-control graph traversal (reports-to walk, department-tree walk, project-assignment lookup, PP HR-line walk) is one indexed query per graph per request; empty target-set input performs zero queries; policy/target reads for one request share a single transaction. Supports the 500-record/2-second §7 NFR jointly with user-management's list endpoint. Binds: access-control. Rule: reportsToUserId, departmentId (User and Department.parentId), and project-assignment foreign keys are indexed; recursive resolution uses a recursive CTE, not N+1 application-side loops.
