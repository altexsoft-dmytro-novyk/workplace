## Verdict

**Changes required before finalizing AD-4.**

The core design is implementable on the repository's current PostgreSQL, Prisma 7.10, and NestJS 11 stack, and the named brownfield seams are accurate. One material database-integrity gap remains: the proposed partial unique index does not require an FR role key and therefore does not fully enforce the stated FR identity model. There is also one current-versus-target ambiguity in the composition diagram.

## Findings

### 1. High — the proposed FR unique index permits multiple keyless FR rows

AD-4 says `targetRole` is the FR role key and the companion amendment says a partial unique index on `targetRole WHERE type='FR'` prevents duplicate FR role keys. PostgreSQL does enforce uniqueness over the indexed FR subset, but unique indexes treat `NULL` values as distinct by default. The proposed type-shape `CHECK` constrains only `targetType` and `targetId`; it does not require `targetRole` for FR rows. Consequently, the database can accept multiple `type='FR'` rows with `targetRole IS NULL`.

That weakens the committed model in three ways:

- `Policies.id` can identify FR rows that have no canonical role key.
- The database does not enforce the asserted “role key” invariant.
- malformed keyless FR rows can accumulate even though authorization happens to ignore `targetRole`.

**Required correction:** explicitly require `targetRole IS NOT NULL` for FR rows, preferably in the type-shape `CHECK` (and decide the allowed AR shape separately). `NULLS NOT DISTINCT` is available in PostgreSQL 18, but a not-null FR shape expresses the business invariant more directly. Also test insertion of a keyless FR row and duplicate `hr-admin` rows at the database boundary.

Primary evidence:

- [PostgreSQL 18 unique indexes](https://www.postgresql.org/docs/18/indexes-unique.html) — nulls are distinct by default; `NULLS NOT DISTINCT` changes that.
- [PostgreSQL 18 partial indexes](https://www.postgresql.org/docs/18/indexes-partial.html) — a partial unique index enforces uniqueness only among rows satisfying its predicate.
- Local contract: `docs/architecture/database-schema.md:191-211`.

### 2. Medium — the migration mechanism is feasible but not committed clearly enough

The PostgreSQL claims themselves are valid:

- the two-arm `CHECK` can enforce the FR/AR target shape when `type` is required and limited to `FR|AR`;
- `PRIMARY KEY (policyId, permissionId)` prevents duplicate grants;
- a reverse `(permissionId, policyId)` B-tree index fits a permission-first equality join;
- a partial unique index can constrain FR role keys.

Prisma 7.10 cannot represent PostgreSQL `CHECK` constraints in `schema.prisma`; they require custom migration SQL. Prisma can model partial indexes only through the `partialIndexes` preview feature, which this repository has not enabled. The repository already uses hand-authored SQL for both `CHECK` and partial unique indexes in `prisma/migrations/20260830010000_access_control_relationships/migration.sql`, so raw SQL is the lowest-risk established pattern.

**Required clarification:** state that ACM-1 must use a reviewed custom SQL migration for the `CHECK` and either (a) the same raw-SQL pattern for the partial unique index or (b) an explicit, separately approved adoption of Prisma's preview feature. Without this, `schema.prisma` alone cannot produce the committed database guarantees.

Primary evidence:

- [Prisma database feature matrix](https://www.prisma.io/docs/orm/v7/reference/database-features) — `CHECK` is not representable or generated by Prisma Migrate.
- [Prisma unsupported database features workflow](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/unsupported-database-features) — customize a migration before applying it.
- [Prisma partial indexes](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/indexes) — `where` requires `partialIndexes`.
- [PostgreSQL 18 multicolumn indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html) — leading-column equality supports the permission-first index choice.
- Local versions/config: `services/backend/package.json:40-42,66`; `services/backend/prisma/schema.prisma:1-6`.

### 3. Medium — the composition diagram reads as current state, but `AppModule` does not import Access Control

The AD-3 Mermaid diagram draws `AppModule --> AccessControl facade`. In the live repository, `AppModule` imports `UserManagementModule` but not `AccessControlModule`; `UserManagementModule` binds `ACCESS_CONTROL_PORT` to `InterimAccessControlAdapter`. `access-control.module.ts` explicitly documents that it is not imported yet.

The surrounding prose describes root composition as future ACM-8 work, so this is not an architectural contradiction, but the diagram is an unlabelled brownfield misrepresentation under a current-reality lens.

**Required correction:** label that edge as the ACM-8 target state, or distinguish “current” and “after ACM-8” composition.

Local evidence:

- `services/backend/src/app.module.ts:8-19`
- `services/backend/src/access-control/access-control.module.ts:7-14`
- `services/backend/src/user-management/user-management.module.ts:32-37`

## Confirmed brownfield claims

- **Live global call sites are exact.** `UsersController` applies `user-management:list` to `GET /users`, `user-management:create` to `POST /users`, and `user-management:deactivate` to `DELETE /users/:id`. The remaining three handlers use target-scoped features and are correctly excluded from the three-key Kernel MVP: `services/backend/src/user-management/application/controllers/users.controller.ts:39-44,58-75,80-112`.
- **The interim position rule is live and noncompliant with AD-4.** `InterimAccessControlAdapter.isAllowed` first limits the three global keys, loads the actor, then authorizes with `actor?.position === 'HR Admin'`: `services/backend/src/user-management/infrastructure/interim-access-control.adapter.ts:11-27`.
- **`targetRole` is absent from runtime TypeScript.** Repository search under `services/backend/src/**/*.ts` returned no match.
- **No `/roles` HTTP surface exists.** The only live controller roots are `users` and `health`; no role controller file exists under `services/backend/src`.
- **No FR persistence exists yet.** The live Prisma schema contains only `User`, `Relationship`, and `Project`; no `Policies`, `Permissions`, `PolicyPermissions`, or `UserPolicies` model exists.
- **The seed claim is substantially accurate but should be read conditionally.** When configured, the live seed creates only the root user and sets `position: 'HR Admin'`; it creates no role attachment. If `ROOT_WORK_EMAIL` is absent, however, the current seed warns and exits successfully rather than failing. AD-4's fail-atomically rule is therefore a future behavior change, not current behavior: `services/backend/prisma/seed.ts:16-29,46-56`.
- **Nest kernel testing is supported.** Current Nest documentation confirms `Test.createTestingModule({ imports: [...] }).compile()` bootstraps a module and dependencies, so the direct-facade integration gate is technically valid: [NestJS testing](https://docs.nestjs.com/fundamentals/testing).
- **Atomic, idempotent seed implementation is supported but must be designed deliberately.** Prisma 7 supports transactions and upserts; uniqueness constraints are necessary for idempotency, and concurrency behavior still needs tests: [Prisma transactions](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions).

## Validation obligations

### Automation candidates

- Migration test rejects FR rows with null `targetRole`, non-null FR targets, null AR targets, duplicate FR keys, and duplicate policy-permission pairs.
- Seed integration tests cover absent, blank, unmatched, inactive, duplicate invocation, and concurrent invocation of `ROOT_WORK_EMAIL`, asserting rollback and exactly the approved rows.
- HTTP regression tests prove the three existing global controller call sites retain their exact feature keys until the consumer rebind story is approved.
- Static architecture check prevents `targetRole`, role-name, or `User.position` comparisons from entering the functional-role evaluator.

### Manual validation

- Review generated/custom migration SQL before apply; Prisma schema review alone cannot validate the `CHECK`.
- Inspect the migrated PostgreSQL catalog (`pg_constraint`, `pg_indexes`) to confirm the actual constraints and predicates.
- During ACM-8, inspect the Nest provider graph and run the separate real-HTTP consumer gate; the kernel integration gate is not evidence that `/users` uses the new facade.

## Scope conclusion

No current framework or database capability invalidates AD-3 or the main AD-4 approach. The architectural choices are supported by current primary sources and repository evidence, but the FR role-key nullability hole must be closed and the raw-SQL migration boundary made explicit before the database guarantees can be treated as committed and enforceable.
