# Epic 3 Context: Career Timeline

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

This epic delivers the `UserEvents` career-timeline log: the system automatically writes an event whenever a tracked change happens on a `User` (currently `joined_company` on create and `position_change` on edit — the only two triggerable types today), and PP/Manager-line (UM) can manually add backfill entries or correct a wrongly-inferred one. A correction is never an in-place edit — it's modeled as soft-delete the wrong entry, then append a new one, so the timeline stays an append-only log of immutable facts. Own resource (`UserEvents`/`/users/:id/events`).

**Blocking dependency — read before starting any story here.** Per `epics.md`'s Epic Sequencing section: "Epic 3 is a genuine sequence point — its auto-write hooks attach to Epic 1's own mutation code paths (e.g. `position_change` fires from the same `PATCH /users/:id` handler Epic 1 builds), so it can't start until Epic 1's handlers exist." Unlike Epic 2 (which only needs a `User` row to exist, seeded directly via Prisma in its own test module — Epic 1 and Epic 2 build in parallel), Story 3.1's auto-write hooks call out *from inside* Epic 1's own `register-user.service.ts` (`POST /users`, Story 1.1) and `edit-user.service.ts` (`PATCH /users/:id`, Story 1.2) code paths. Those files must actually exist as real, mergeable code before Story 3.1's hooks can be wired in — this epic is not parallelizable with Epic 1, and should not be started against a stubbed or fixture-only version of those handlers.

## Stories

- Story 3.1: System Auto-Generates Career Timeline Events
- Story 3.2: PP/Manager-Line Manually Adds a Backfill Entry
- Story 3.3: PP/Manager-Line Corrects or Deletes an Event

## Requirements & Constraints

- Only `joined_company` (on `POST /users` success) and `position_change` (on `PATCH /users/:id` when `position` actually changes) have a triggering code path today. The other six documented `UserEvents.type` values (`grade_change`, `department_change`, `employment_type_change`, `extended_leave`, `mentorship_start`, `mentorship_end`) reference contexts that don't exist yet (grade/department/employment-type/leave tracking; mentorship pairing lands in Epic 4). Don't build system hooks for those six. A manual `POST /users/:id/events` may still carry any of the eight documented `type` values as free-form data (see `um-ct-03`'s manually-added `mentorship_end` backfill) — there's simply no system-side trigger for six of them yet.
- Manual add and manual correct/delete are gated to two sourced actors only: the target employee's People Partner (PP) and their Manager-line (Bob, Alice's *unit manager* — not the full manager chain up to the org root). §4.9 names PP and UM specifically, not "any manager."
- Corrections are never an in-place update. §4.9's "correct events the system inferred wrongly" is: soft-delete the wrong entry (`DELETE /users/:id/events/:eventId` → `deletedAt` set), then append a new entry (`POST /users/:id/events`) with the right data. Both steps are separately attributable HTTP calls, and both rows persist in the underlying table — only the wrong one drops out of reads.
- A soft-deleted entry is excluded from `GET /users/:id/events` entirely — never returned with a null/placeholder body, and never exposing `deletedAt` to the caller ("absence is absence," per the test-case suite's own README convention).
- `UserEvents` entries are immutable facts once written: no field on an existing row is ever mutated after creation except `deletedAt` going from `null` to a timestamp.
- Every entitlement check (PP-of-target, Manager-line-of-target) goes through the shared `AccessControlPort` facade's target-scoped check — the same seam Story 1.2 introduced for `PATCH /users/:id` — never inline role/policy logic in a controller or action.
- `UserEvents` carries pseudonymised data only outside production, same as `User` (NFR-1) — no real personal data in fixtures, logs, or the repo.
- This suite covers workflow/data correctness only, not who is entitled to do it — entitlement itself is access-control's own suite's job, same division of labor as Epic 1 (`epic-1-context.md`).

## Technical Decisions

- **Binding implementation constraint (AD-11), applies to every tracked-change hook this epic wires:** system-triggered `UserEvents` writes happen **synchronously, in the same transaction** as the domain mutation that causes them, via an **explicit call** from that use-case's own code (e.g. `register-user.service.ts` calls a write-event operation directly as part of creating the `User`; `edit-user.service.ts` does the same when the patch changes `position`). No event bus, no generic table-change listener/trigger, no `EventEmitterModule`-style pub/sub — even though NestJS makes that pattern easy to reach for, it is explicitly barred here. Story 3.1 establishes this pattern for `joined_company`/`position_change`; any later story that wires a new tracked-change hook (e.g. Epic 4's Story 4.2 mentorship-pairing hook) follows this identical one pattern, not a variant.
- `UserEvents` has **no Prisma model yet** — per `database-schema.md`'s documented shape (`id` uuidv7 PK, `userId` FK → `User`, `type` string, `eventDate` date, `details` jsonb, `source` `'system'|'manual'`, `deletedAt` nullable timestamp, `createdAt`, `createdBy` FK → `User`). Adding this model plus its migration is a prerequisite for any of this epic's tests to go green, and is Story 3.1's job as the first story in the epic — Stories 3.2 and 3.3 depend on that schema landing first and do not re-derive or alter it.
- Router shape (AD-14, `api-conventions.md` shape 2, owned collection): `POST /users/:id/events` (create — system-sourced or manual), `GET /users/:id/events` (list, excludes soft-deleted), `DELETE /users/:id/events/:eventId` (soft-delete). No `PATCH` on a single event — correction is soft-delete + append, never an in-place field update, so no update handler exists on this resource by design.
- Standard hexagonal layout, same as Epic 1: `application/` (controller, DTOs, actions), `domain/` (entity, port interfaces, services), `infrastructure/` (Prisma repository, fakes). Domain code imports nothing from Prisma, NestJS transport, or HTTP.
- Every entitlement check goes through the shared `AccessControlPort` facade's target-scoped check (the same seam Story 1.2 introduced), never a direct role-flag or policy-table read inside a user-management controller.
- Quality gate: same AD-1 three-stage gate as every other epic in this domain — an approved scenario document before an E2E test is written, and an E2E test that exists and is red before production code is written. `um-ct-01` through `um-ct-07` already have draft scenario docs pending approval under `docs/test-cases/user-management/career-timeline/` — reuse and get them approved, don't rewrite from scratch. An E2E test file already exists on the backend submodule's separate `user-management` branch (commit `865df5f`) at `test/user-management/career-timeline.e2e-spec.ts`, covering all seven cases against one shared Alice (plus Nina for `um-ct-01`) — reconcile/extend it during each story's stage-2 checkpoint, do not recreate it.
- `um-ct-05`'s precondition (a wrongly-inferred system entry) has no HTTP-observable way to manufacture directly — no request can force a genuine bad inference on purpose. The existing E2E file seeds an equivalent wrong entry through the same manual-add endpoint `um-ct-03`/`um-ct-04` already exercise, flagged in-file with a comment; this substitution doesn't change the mechanic under test (soft-delete the wrong entry, append the correction), and Story 3.3 should preserve that approach rather than inventing a different seeding mechanism.

## Cross-Story Dependencies

- Story 3.1 is the schema owner: it adds the `UserEvents` Prisma model and migration, plus the repository and `GET /users/:id/events` needed to observe its own writes. Stories 3.2 and 3.3 build their manual-add/soft-delete code paths against that same model and do not re-add or alter it.
- Story 3.1's hooks into `register-user.service.ts` and `edit-user.service.ts` (Epic 1) must land before Story 3.1 is considered done — this epic cannot be split so that 3.2/3.3 start before 3.1's schema and hooks exist, since the shared `UserEvents` table and its repository are common infrastructure every later story in this epic reads and writes.
- Story 3.2's manual-add code path (controller handler + action + domain service for `POST /users/:id/events`) is reused as-is by Story 3.3's "append the corrected entry" step — Story 3.3 does not duplicate that write path, only adds the soft-delete (`DELETE /users/:id/events/:eventId`) path alongside it. Story 3.3 also depends on Story 3.2 landing first for a second reason: the existing E2E file's `um-ct-05` precondition and `um-ct-06`'s target event are both seeded through Story 3.2's manual-add endpoint.
- Story 3.3's soft-delete path is a prerequisite for both of its own acceptance criteria (correct-via-replace, and delete-with-no-replacement) — one `DELETE` handler serves both.
- This epic builds on Epic 2 for authenticated PP/UM sessions on the manual-add/correct/delete paths (Stories 3.2, 3.3) — Story 3.1's system-triggered writes need no separate authentication of their own, since they ride inside an already-authenticated `POST /users`/`PATCH /users/:id` request.
