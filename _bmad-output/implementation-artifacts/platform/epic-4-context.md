# Epic 4 Context: Access Control Authorization Consolidation

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Collapse the per-section authorisation predicates scattered across User Management's access-control adapter into one section-parameterised gate driven by `AccessControlFacade.canAccessSection`, rename legacy `S<n>` section keys to human names (`profile:identity`, …), and record a single, non-drifting rule for composing the functional-permission ("feature") half of a write check with the audience/section half. The epic exists because a 2026-09-03 code review found the drift already happening in production code: an ad-hoc `user-management:edit` OR-override had been added to `canEditS1` so a dev script could give root universal edit — directly violating the invariant that a functional role never widens data access. Fixing this matters because every future section (`profile:timeline`, `profile:mentorship`, …) would otherwise repeat the same hand-written predicate and the same risk of a feature permission silently bypassing the audience-derived matrix decision. The epic also seeds a real reporting tree and full-profile grant at the root identity so that root's admin power comes from the ordinary audience-resolution path instead of a functional-role special case.

**Note on epic numbering:** the epics file (`_bmad-output/planning-artifacts/platform/epics.md`) contains two unrelated sections both titled "Epic 4" — this one ("Access Control Authorization Consolidation", tracked in `sprint-status.yaml` under `epic-4` / sprint keys `4-1-…` and `4-2-…`) and a separate, untracked "Project-Line Audience" epic. This context covers only the tracked epic, matching the two known story tickets.

## Stories

- Story 4.1: Generalise section-access authorisation + human section keys
- Story 4.2: Default org-relationship seed + retire the identity-card FR override

## Requirements & Constraints

- Enforces the §3.2 section-access matrix (PM-FR-3) as a hardening pass over the kernel MVP's narrow S1/S10/S11 substrate — no new section coverage, just one consistent gate mechanism.
- No `S<n>` string may appear as a section identifier anywhere in backend `src/` or `test/`; `canAccessSection` and every caller must use human-named keys, with `S<n>` surviving only as a matrix-row citation in docs.
- A functional role (FR) may never widen data access: feature permissions operate only within audiences already resolved for the viewer. Any authorisation predicate that lets an `isAllowed(...)` check substitute for or override an audience/section check is an invariant violation and must be removed, not special-cased.
- A write requires both dimensions to permit it: `isAllowed(viewer, feature)` AND `canAccessSection(viewer, section, target) === 'write'`. Matrix-only or feature-only checks are insufficient (§2.2 dual gate). The identity card follows this same dual-gate shape as every other section (reversing an earlier "audience-only" resolution).
- HR Admin is a configuration-only functional role: it grants no default data access by itself. A delegated HR Admin (functional role only, no relationship to the target) gets the full admin feature set but zero profile data access beyond what their own reporting-line/PP/full-profile position independently grants.
- Every story in this epic runs the full AD-1 three-stage gate per increment (scenario prose → independent human approval → approved red E2E → production code); no dispatch spans two stages, and sub-parts of a story (4.1a–d, 4.2a–c) are separate AD-1 dispatches.
- Any change under `services/backend/src/access-control/**` invalidates the pinned ACM-9 performance baseline; a story is not done until an ACM-9 rerun (protocol `ACM9-MVP-v1`, 500 targets, warm p95 and worst case ≤ 2s) covers the shape the story introduced.
- Out of scope: Profile Projection field/record narrowing (still its own deferred story — this gate only decides `none`/`read`/`write`, not which fields); global-feature default holders (`directory:*`, `admin:*`, role management); the department-management and project-line audience branches (separate pending increments); root's write access to `profile:personal-contacts` / `profile:emergency-contacts` / `profile:documents` (reporting-line audience is read-only there by design).

## Technical Decisions

- **`DEFAULT_PERMISSIONS` baseline (D2, 2026-09-04).** A code constant lists the per-person section-write keys (`profile:identity:write`, …) that every **active** employee implicitly holds. `isAllowed(user, key)` = `key ∈ DEFAULT_PERMISSIONS` (active user) ∪ the existing data-driven FR grant chain. This is FR-tier only: an in-memory set check, no relationship read, no hot-path scan, no `employee` `Policies` row, no `PolicyPermissions`, no `UserPolicies` attachment, no seed/bootstrap/migration change. The engine stays allow-only — narrowing a section means removing its key from the baseline and granting it explicitly to a tighter role; there is no per-individual carve-out.
- **Single gate mechanism (D3).** One `@RequireSectionAccess('<key>', 'read' | 'write')` decorator/guard (in `application/guards/`) replaces every per-section predicate (`canEditS1`, the `EDIT_USER_FEATURE`/`READ_USER_FEATURE` routing branches). A required level is satisfied by a resolved `SectionAccess` at or above it (`write` satisfies `'read'`). It calls the existing `ACCESS_CONTROL_PORT` seam — no new cross-context coupling. Today only one section→endpoint mapping exists live: `PATCH /users/:id` and the `GET /users/:id` `canEdit` hint both map to `@RequireSectionAccess('profile:identity', 'write')`; `GET /users/:id` data read maps to `'read'`. `profile:leave`/`profile:projects` (the kernel's S10/S11) exist in the matrix but have no route consumer yet.
- **Human section keys (D4).** `canAccessSection` and every caller/scenario/test move from `'S1'`/`'S10'`/`'S11'` to `'profile:identity'`/`'profile:leave'`/`'profile:projects'`, establishing the naming convention future sections (e.g. `profile:timeline`) adopt from day one.
- **Seeded root identity (2026-09-03/04, Winston + Dmytro).** The ACM-0 seeded root holds three separate capabilities from three separate mechanisms: (1) the `hr-admin` functional role for admin features, (2) top of the `reports-to` tree for transitive `reporting`-audience write access, (3) first holder of the §2.4 full-profile-access read-only overlay grant. None of these mechanisms is allowed to leak into the others — the OR-override that let a functional role short-circuit the audience check is deleted; root's edit power must come from its seeded tree position, not an adapter special case.
- **Resolver walk direction.** ~~`resolveAudiences` currently expands every descendant of the viewer then filters to requested targets, which is worst-case at the tree root. It is switched to walk upward from each requested target, bounding the query by chain depth rather than org size~~ — **CORRECTED 2026-09-05: this is already built and is not work in Epic 4.** The upward walk shipped 2026-08-30 in `services/backend` commit `f36d1b2`, an ancestor of HEAD `e0b1a53`; the CTE at `prisma-relationship-graph.adapter.ts:88-120` seeds from the requested targets and ascends. The stale premise reached this file by being copied from a deferred-work entry that was promoted into Story 4.2 without re-verification. The property remains load-bearing for the ACM-9 500-target/2s budget once root sits permanently at the tree root, so it is a property to *evidence* for the seeded shape, not a change to make — and no speedup may be claimed for Epic 4, which changes no query. See `_bmad-output/implementation-artifacts/access-control/solution-design-upward-walk-resolver.md`.
- **Dev-only org seed.** A dev-only script (`db:dev:seed-org`, superseding `dev-grant-root.ts`) builds a two-level fake `type='direct'` reporting spine (one department lead reporting to root; other members reporting to their lead) over seeded/imported population; it throws under `NODE_ENV=production` and stays absent from `prisma/seed.ts` and `bootstrap-access-control.ts`. Production root-operator provisioning (the FR grant set and the tree-root/full-profile seeding) is a separate, non-dev-only path in `bootstrap-access-control.ts`.
- **AR vs FR separation holds throughout.** Policy evaluation stays type-separated (FR checks never enter the AR hot path and vice versa); an AR policy attachment (e.g. PM/DM project grant) only grants access when joined to a live matching relationship row — fail-closed otherwise.
